# Operations

> Part of the [Feature Map](../README.md) — Last reviewed: 2026-11-04

## Overview

The generic **confirm → sign → submit** pipeline shared by every operation type that produces an on-chain extrinsic —
transfers, staking, governance, fellowship actions, proxy management, and multisig approve/reject. A user never
navigates to "Operations" directly; every other feature that ends in a signature routes through this one so that
validation, wallet-specific signing, and submission status handling are implemented once.

## Who can use it / when it applies

Consumed internally by any feature whose flow ends in signing an extrinsic. This feature owns the shared shell; each
operation type supplies its own confirmation content and validation rules through it (see below) rather than
reimplementing sign/submit itself.

## States / scenarios

| Area                       | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`OperationsConfirm`**    | Per-operation-type confirmation screens (one subfolder per type — Transfer, staking actions, governance actions, proxy actions, fellowship actions). Each renders its own summary and amount, but shares common building blocks (`common/`: the multisig-exists alert, the operation-description field, the call-data and signing-path sections). The dashboard staking flows (amount, confirm, reward destination) share one confirm-store factory from here (`OperationsConfirm/lib/createFlowConfirmModel`), so their confirm screens are bound to the same wallets, apis and pending multisig operations. The multisig-exists alert (which also hides the Sign button) fires when the call placed inside the multisig matches an operation still pending on the same chain — for a flexible multisig or a proxied account behind a multisig that is the proxy call, not the bare action. A call whose hash cannot be computed is not reported as a duplicate: the sign step refuses it with the "couldn't prepare this operation for signing" screen instead.                                                                                                                                                                                                    |
| **`OperationsValidation`** | Per-operation-type validation rule sets that decide whether a confirmation can proceed — balance and existential-deposit checks plus operation rules such as the staking minimum bond — feeding each type's `canSubmit` gate. Every rule kind renders through the shared `TransactionValidationError` alert, so a transfer and a staking form report problems the same way.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **`OperationSign`**        | Wallet-specific signing UI, switched by wallet type: Polkadot Vault (QR scan), browser Extension, WalletConnect, or a watch-only placeholder (which cannot sign). A WalletConnect session that was not approved for the transaction's chain is not asked to sign — the flow stops on a reconnect prompt first (see `wallet-connect-wallet`). Whatever the wallet type, every returned signature is checked against its own transaction and signer (and the number of signatures must match the number of transactions) before submission; a mismatch stops the flow with an "invalid signature" error before the balance is checked, and a balance that no longer covers the operation stops it with the balance error. Plain and type-prefixed (Polkadot Vault multi-frame, incl. ECDSA) signatures are accepted. Which bytes a signer signs is owned by the network domain (`transactionService.verifyPayloadSignature`), so both signing and submission verify through it. A batch too heavy for one extrinsic is split into several before signing — each part keeps the original batch method and the signer is warned about the split. A batch that fits is signed as is, and a multisig call is never split (co-signers must see and approve the exact call). |
| **`OperationSubmit`**      | Submits the signed extrinsic and shows the status modal: in progress → success (auto-closing) or error (dispatch/submission failure). Submission uses the signed payloads directly: each extrinsic is rebuilt from the payload the signer actually signed and paired with its own signature and signatory, so a batch that was split before signing is never split again on the way out. A signature count that differs from the payload count, or a signature that none of the operation's signatories made, stops the flow with a localized error (nothing signed / count mismatch / unknown signatory) instead of submitting; such a failure does not finish the flow, and the next submission starts from a clean status.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **`OperationBlocked`**     | The shared "this operation can't be prepared" screen, shown in place of a confirmation that never became ready. Takes a typed reason (network turned off, unreachable, busy or unresponsive node, fee estimation failed, no signatory, unusable signing path, invalid call data, call that cannot be encoded, call too heavy to sign, internal) and renders the matching explanation naming the chain, plus only the remediations that fit it — try again, change node, open network settings, reload, close.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **`OperationMessageSign`** | The parallel flow for signing an off-chain message (not an extrinsic) — e.g. the address-book backend's auth challenge.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

## An operation without an amount

Most confirmation screens lead with the amount the user is about to move. **Claim rewards** cannot: the call names an
(era, validator, page) and the runtime settles what that page owes at execution, so any figure shown beforehand is a
prediction that can differ from what lands. Its confirmation therefore states the _scope_ of the claim — how many
payouts, over how many eras, across how many validators — and validates only what is genuinely in question, which is
whether the payer can afford the fee.
