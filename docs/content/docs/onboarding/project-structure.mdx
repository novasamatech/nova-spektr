Nova Spektr is both a web and Electron app. This is reflected in the file structure, which follows Electron guidelines.
Source code is separated into 3 build targets:
- `main` - electron's main process that executes in node.js sandbox.
- `renderer` - web application.
- `preload` - bridge between electron and browser environment. Source code is contained in `main` directory.

## Top-level directories

<FileTree>
  - scripts/ build scripts and other helpers
  - config/ project config
  - tests/ end-to-end tests
  - docs/ dev documentation
  - src/
    - main/
    - renderer/
      - ...
</FileTree>

## Renderer structure

<FileTree>
  - app/ app entry point, bootstrap code
    - index.html
  - domains/ core business logic
  - aggregates/ shared state and logic
  - features/ user flows implemented as separated modules
  - sdk/ simple way to integate features and domains
  - pages/ combination of features
  - shared/ helpers, utils, integrations
  - entities/ **deprecated** logic and ui for given entity (e.g. wallet, chain, etc.)
  - widgets/ hook-consuming UI components (access data via useUnit, useStoreMap, etc.)
</FileTree>

## Domain

Domains encapsulate core business logic while providing a clean, intuitive contract for interaction.

### Folder structure
<FileTree>
  - domain-name
    - _lib/ code not related to actual business logic
      - helpers.ts
      - types.ts
    - entity
      - store.spec.ts
      - store.ts effector storage with related logic
      - resource.ts (optional) transport + mappings
      - service.spec.ts
      - service.ts stateless service
      - types.ts public interfaces
    - entity-2
      - ...
    - index.ts
</FileTree>

### `index.ts`

Each domain's entry point **must**:
- Expose only necessary abstractions.
- Present a self-documenting API surface.

The goal is to create interfaces so transparent that they almost narrate the domain's purpose through their structure.

### store

Domain's store **must**:
- Export single object without `Store` or `Model` suffix (`accounts`, not `accountsStore`).
- Provide stores and methods.
- Create integrations with data sources.
- Be isolated, no other stores in dependencies.
- Be testable.

Store file should export single object with same name as entity.
Public API should be as simplest as possible and consist mostly from storages and effects.
All effector storages should be readonly.
Exported effects should be named as meaningful actions (with CRUD prefixes or verbs).

```ts title="store.ts" frame="code"
export const accounts = {
  $list: readonly($list),
  $populated: readonly($populated),

  populate: populateFx,
  createAccounts: createAccountsFx,
  deleteAccounts: deleteAccountsFx,
  /* ... */

  __test: {
    /**
     *  In case of complex internal flows
     *  some stores/effects can be exposed for mocking in unit tests
     **/
  },
}
```

### service

Domain's service **must**:
- Export a single object named as `singular entity name + 'Service'` (e.g. `accountService`).
- Provide meaningful business actions (no internal logic or external data mapping)
- Be stateless

```ts title="service.ts" frame="code"
function isChainAccount(account: AnyAccount) {
  /* implementation */
}

export const accountService = {
  isChainAccount,
  /* ... */
};
```

## Aggregate

An aggregate is a model that contains contextual data.
Unlike a domain model, an aggregate can store user-specific state.
For example, a selected wallet or network for working within a specific feature.

### Folder structure

<FileTree>
  - aggregate-name
  - model.ts
  - service.ts (optional)
  - index.ts
</FileTree>

## Feature

Features are the connecting link between domain logic and the user.
They are responsible for implementing specific user scenarios and corresponding interfaces.
A feature can be integrated with other features through Dependency Injection (DI), creating a composition of scenarios for a more global flow.

Feature **must**:
- Contain one or few related user flows. E.g. `fellowship-evidence` and `fellowship-profile` are separate features because of different flows.
- Export feature identificator created with `createFeature` factory.
- Be written as standalone module with integrations in feature identificatior (`feature.inject(...)`).

Feature **can**:
- Export components and events related to internal logic.

Feature **must not**:
- Export any store or logic with data access. Data should be store eather in domain of aggregate. Feature can implement own data request or storage logic but it should be scoped inside.

### Folder structure

<FileTree>
  - feature-name
    - ui/ React components only
    - hooks/ custom React hooks
    - model/
      - feature.tsx
      - ...
    - index.tsx
</FileTree>
